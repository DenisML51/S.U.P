# Архитектура

## Принципы

1. **Лист персонажа — документ игрока.** Он хранится целиком (JSON-документ со схемой и версией),
   а не разложен по таблицам. Игрок редактирует его сам, конфликтов «между пользователями» нет —
   есть только разные устройства одного игрока.
2. **Local-first.** Источник правды для интерфейса — локальная копия в IndexedDB. Любое действие
   применяется мгновенно, работает без сети и уходит на сервер в фоне.
3. **Одни правила для всех.** Схема и игровые правила — общие пакеты, которые импортируют и
   клиент, и сервер. Формулы не дублируются ни в компонентах, ни на сервере.
4. **Сервер — хранилище и шина.** Он проверяет документы по общей схеме, разрешает конкурентные
   записи по ревизиям и оповещает остальные устройства. Когда появится совместная игра (лобби,
   бой), авторитетные вычисления (HP в бою, броски) будут жить там же, на `@itd/game-logic`.

## Пакеты

```
@itd/schema       ← ни от чего не зависит (кроме zod)
@itd/game-logic   ← @itd/schema
apps/api          ← @itd/schema
apps/web          ← @itd/schema, @itd/game-logic
```

### `@itd/schema`

- `CharacterSchema` — версия 1 документа. Парсинг одновременно нормализует: проставляет значения
  по умолчанию и приводит то, что приходит из форм (`NaN`, `null`, числа строкой). Неизвестные поля
  сохраняются: в листах бывают свои метаданные, терять их нельзя.
- `migrateCharacter()` — единственный вход для внешних данных (импорт, сервер, старые сохранения).
  Цепочка миграций `v0 → v1 → …`; v0 — все листы десктопной версии.
- `mergeCharacters(base, local, remote)` — трёхстороннее слияние для синхронизации: изменения
  разных полей объединяются, списки сущностей (предметы, заклинания…) сливаются поштучно по `id`,
  история объединяется, при настоящем конфликте поля побеждает локальная правка.
- `revertCharacter(before, after, current)` — отмена правок тем же слиянием (предок — `after`):
  изменения с других устройств, сделанные после правки, сохраняются.
- Контракты HTTP/WebSocket (`api.ts`): схемы запросов валидирует сервер, типы ответов использует
  клиент.

### `@itd/game-logic`

Контент системы (расы, классы, навыки, состояния, травмы, таблица опыта) и правила — чистые
функции `Character → Character` или `Character → число`: модификаторы, класс брони героя и
конечностей (вычисляется из снаряжения, плюс ручной бонус), рассудок, конечности, прогрессия,
point-buy, инвентарь (экипировка с эффектами), ресурсы и отдых (короткий/долгий, кости хитов,
правило восстановления у ресурса), концентрация, экономика действий и `performAction`
(использование атаки/способности/заклинания с оплатой ресурса и боеприпасов), броски кубиков
(`1d6+2`, `1к8`, «… и …»), создание персонажа.

`upgradeCharacter` приводит сохранённый лист к текущим правилам (то, что схема сделать не может,
потому что не знает правил): границы рассудка и хитов конечностей, ручной бонус КБ из старого
сохранённого итога. Клиент вызывает её при каждом чтении документа из IndexedDB и перед правкой.

## Сервер (`apps/api`)

Fastify 5, Drizzle ORM, PostgreSQL. Модули: `auth`, `characters`, `realtime`.

### Аутентификация

- Пароли — argon2id. Регистрация может быть закрыта (`REGISTRATION_ENABLED=false`), тогда аккаунты
  создаёт CLI.
- Access-токен — JWT на 15 минут, живёт только в памяти вкладки.
- Refresh-токен — случайная строка в httpOnly-куке `SameSite=Strict` с путём `/api/auth`; в базе
  хранится только её хеш. При каждом обновлении токен ротируется. Повторное использование старого
  токена считается кражей и завершает всю цепочку сессий; одновременное обновление из двух вкладок
  укладывается в 30-секундное окно и кражей не считается.
- Эндпоинты на куке требуют заголовок `x-itd-client` (защита от CSRF поверх SameSite).
- Смена пароля завершает остальные сессии и закрывает их WebSocket.

### Персонажи и синхронизация

| Метод                                   | Назначение                                         |
| --------------------------------------- | -------------------------------------------------- |
| `GET /api/characters?since=<курсор>`    | изменения после курсора (включая удаления)         |
| `PUT /api/characters/:id`               | создать/обновить: `{ baseRevision, data }`         |
| `DELETE /api/characters/:id?baseRevision=` | удалить в корзину                               |
| `POST /api/characters/:id/restore`      | восстановить из корзины                            |
| `GET /api/characters/deleted`           | корзина                                            |
| `GET /api/characters/:id/revisions[/:n]`| точки восстановления                               |

- **Ревизии.** Запись проходит, только если `baseRevision` совпадает с текущей; иначе `409` с
  текущей записью, чтобы клиент слил изменения без лишнего запроса.
- **Курсор.** Каждая запись берёт следующее значение счётчика пользователя, обновляя строку
  пользователя. Эта блокировка упорядочивает записи одного игрока, поэтому номера изменений
  фиксируются строго по возрастанию и выборка «всё после курсора» ничего не пропускает.
- **Удаление мягкое.** Строка остаётся «надгробием», чтобы другие устройства узнали об удалении;
  запись поверх удалённого персонажа восстанавливает его (правка важнее удаления).
- **Точки восстановления** сохраняются не чаще раза в 10 минут, хранятся последние 50.

### Realtime

`GET /api/ws`. Токен передаётся первым сообщением, а не в URL (не попадает в логи прокси). Сокет
только сообщает «персонажи изменились» — данные клиент забирает по HTTP. Уведомления идут через
Postgres `LISTEN/NOTIFY`, поэтому их получают клиенты любого инстанса API, а запись из CLI тоже
долетает до открытых вкладок.

## Клиент (`apps/web`)

```
src/data/
  api/client.ts            HTTP-клиент: токен из памяти, один refresh на 401, ошибки сети отдельно
  session/sessionManager   вход/выход, ротация токена, Web Lock между вкладками, кэш профиля
  local/database           IndexedDB (Dexie), своя база на каждый аккаунт
  local/characterRepository  чтение/запись, атомарные правки, применение серверных изменений
  sync/syncEngine          выгрузка, подтягивание по курсору, слияние при 409, ретраи
  sync/realtimeClient      WebSocket с переподключением → запуск синхронизации
  workspace.ts             всё вышеперечисленное для одного вошедшего пользователя
src/store/
  useSessionStore          состояние входа и синхронизации для UI
  useCharacterStore        открытый персонаж и список; API для компонентов
```

Поток одной правки: компонент → `updateCharacter(prev => …)` → UI обновляется сразу → правка
применяется к последней сохранённой версии внутри транзакции IndexedDB → через ~0,8 с
синхронизация отправляет документ → другие устройства получают уведомление и подтягивают его.

Отмена: стор хранит снимки «до/после» правок открытого персонажа (до 50 за сессию, не в документе).
Отмена — обычная правка (`revertCharacter` на свежей версии), поэтому она синхронизируется и не
затирает изменения с других устройств.

Правки внутри транзакции применяются к свежей версии, а не к той, что была на экране. Поэтому
изменение, пришедшее с сервера, пока игрок что-то нажимал, не затирается.

Без сети приложение стартует из кэша (профиль и локальная база) и досинхронизируется, когда сеть
появится. При выходе локальная база удаляется; если есть неотправленные изменения, приложение
предупреждает.

## Инфраструктура

- `docker-compose.yml`: `postgres` → `api` (миграции применяются при старте, healthcheck по БД)
  → `web` (nginx без root, SPA, прокси `/api` и `/api/ws`). Снаружи открыт только порт 3000.
- Образ API: бандл tsup с встроенными общими пакетами на `node:22-alpine`, запуск не от root,
  корректное завершение по SIGTERM.
- Конфигурация API — переменные окружения, проверяются zod при старте (`apps/api/src/config.ts`).
